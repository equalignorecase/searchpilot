# SearchPilot

เว็บวิเคราะห์ข้อมูล Google Search Console สำหรับเจ้าของคนเดียว ใช้ Next.js App Router, TypeScript แบบ strict, Tailwind/shadcn primitives, Recharts, TanStack Table, Neon Auth แบบจัดการให้, Prisma 7 พร้อม Neon adapter และ googleapis SDK ทางการ

หน้าจอเป็นภาษาไทย สไตล์ modern minimal รองรับ Dark mode และใช้ IBM Plex Sans Thai จาก Google Fonts โดยเก็บไฟล์ฟอนต์ในโปรเจกต์พร้อมใบอนุญาต ไม่มีระบบ AI การเรียกเก็บเงิน หน้าสมัครสมาชิก ข้อมูลสถิติจำลองในระบบจริง หรือ Redis

## เริ่มต้นด้วยตัวช่วยตั้งค่า

เปิด Terminal ที่รับการพิมพ์โต้ตอบได้ แล้วรัน:

```sh
npm ci
npm run setup
```

ตัวช่วยจะเปิดหน้าตั้งค่าทางการของ Neon และ Google รับชื่อผู้ใช้และข้อมูลการเชื่อมต่อ โดยซ่อนค่าลับขณะพิมพ์ สร้าง `.env.local` ด้วยสิทธิ์ไฟล์ `0600` เก็บคีย์เข้ารหัสเดิมไว้ สร้าง Prisma Client ใช้ migration กับ branch สำหรับพัฒนาที่เลือก แล้วรัน `npm run check:setup`

จากนั้นตัวช่วยจะตรวจ TypeScript, lint, unit/integration tests และ production build รวมถึงติดตั้ง Chromium ทางการสำหรับทดสอบและรัน Playwright แบบแยกสภาพแวดล้อมจาก Terminal ของคุณ

`check:setup` ตรวจรูปแบบค่าตั้ง การเชื่อมต่อฐานข้อมูลแบบอ่านอย่างเดียว ตารางธุรกิจทั้ง 9 ตาราง และ endpoint ของ Neon Auth โดยไม่พิมพ์ค่าลับ หากข้อมูลหรือการเชื่อมต่อไม่ครบ คำสั่งจะจบด้วยสถานะที่ไม่ใช่ศูนย์

การตรวจนี้ **ไม่ได้ยืนยัน** ว่าเข้าสู่ระบบด้วยรหัสผ่านได้ ขอสิทธิ์ GSC สำเร็จ ใช้ API ได้ หรือซิงก์เบื้องหลังทำงานแล้ว ต้องตรวจขั้นตอนจริงเพิ่มเติม

การเข้าแอปใช้ชื่อผู้ใช้และรหัสผ่าน ส่วนการอนุญาต Search Console ต้องใช้บัญชี Google ในเบราว์เซอร์แยกต่างหาก การ deploy จริงต้องเข้าถึงบัญชี Neon/Vercel หากต้องการให้ผู้ช่วยดำเนินการ ต้องติดตั้งและเชื่อมต่อบริการนั้นก่อน ห้ามวางรหัสผ่าน OAuth Client Secret หรือ URL ฐานข้อมูลที่มีรหัสผ่านในแชต ใช้ขั้นตอนตั้งค่าด้วยตัวเองด้านล่างได้เมื่อไม่มีการเชื่อมต่อบริการ

## รันในเครื่อง

ต้องมี Node 22.12 ขึ้นไป, npm, OpenSSL, บัญชี Neon และโปรเจกต์ Google Cloud โดยไฟล์ซอร์สไม่มีค่าลับของระบบจริงฝังไว้

สำหรับการตั้งค่าครั้งแรกเท่านั้น ให้คัดลอกไฟล์ตัวอย่าง หากมี `.env.local` อยู่แล้ว ให้แก้ไฟล์เดิมและเก็บคีย์เดิมไว้:

```sh
npm ci
cp .env.example .env.local
# กรอกค่าของ branch สำหรับพัฒนาใน .env.local ก่อนทำขั้นต่อไป
npm run auth:owner
npm run db:generate
npm run db:migrate
npm run dev:https
```

เปิดอีก Terminal เพื่อประมวลผลงานซิงก์ โดยไม่ผูกกับการเปิดหน้าเว็บหรือเซสชันเข้าสู่ระบบ:

```sh
npm run worker
```

เปิด https://localhost:3000 และใช้ URL นี้ให้ตรงกับ `NEXT_PUBLIC_APP_URL` รวมทั้งเพิ่มเป็น trusted origin ใน Neon Auth

คำสั่ง HTTPS สร้างใบรับรอง localhost แบบลงนามเองด้วย OpenSSL เก็บใน `certificates/` ซึ่งถูกละเว้นจากการควบคุมเวอร์ชัน ครั้งแรกต้องเชื่อถือใบรับรองสำหรับการพัฒนาในเบราว์เซอร์ สคริปต์ไม่ติดตั้ง certificate authority ลงระบบ และระบุพาธใบรับรองชัดเจนเพื่อป้องกัน Next.js กลับไปใช้ HTTP เมื่อการสร้างใบรับรองอัตโนมัติล้มเหลว

หยุดเซิร์ฟเวอร์ HTTP เดิมก่อนรัน HTTPS คุกกี้เซสชัน Neon ใช้ `Secure` จึงควรใช้ HTTPS ให้สม่ำเสมอทุกเบราว์เซอร์

หากยังตั้งค่าไม่ครบ แอปจะเปิด `/setup` การมีค่าตั้งไม่ได้ยืนยันว่าบริการเชื่อมต่อได้ เมื่อฐานข้อมูลหรือ Google มีปัญหา ระบบจะปฏิเสธการทำงานอย่างปลอดภัย และไม่สร้างข้อมูลจำลองลงตารางธุรกิจ

## 1. ฐานข้อมูล Neon และบัญชีเจ้าของ

ระบบใช้ชื่อผู้ใช้และรหัสผ่านตามข้อกำหนดที่ปรับภายหลัง แทนการเข้าแอปด้วย Google ที่ระบุใน `gsc.txt` ส่วน Google ยังจำเป็นสำหรับอนุญาตการเข้าถึง Search Console

1. สร้างโปรเจกต์ Neon บน AWS และ **branch สำหรับพัฒนา** ใส่การเชื่อมต่อแบบ pooled ใน `DATABASE_URL` และแบบตรงใน `DATABASE_URL_UNPOOLED` โดยเปิด TLS ไว้
2. เปิด **Neon Auth / Managed Better Auth** คัดลอก Auth URL แบบเต็มของ branch ลง `NEON_AUTH_BASE_URL` และเพิ่ม `NEXT_PUBLIC_APP_URL` เป็น trusted origin แอปใช้ SDK ทางการ `@neondatabase/auth` ไม่ได้สร้าง Better Auth server แยก
3. เปิด Email & Password sign-in สำหรับบัญชีเจ้าของใหม่ที่ใช้ตัวระบุภายใน ให้ปิด **Require email verification** และอีเมลยืนยัน แล้วอนุญาต sign-up ชั่วคราวระหว่างสร้างบัญชี ไม่ต้องเปิด Google provider เพื่อเข้าแอป
4. ตั้ง `APP_USERNAME` และสร้าง `NEON_AUTH_COOKIE_SECRET` ด้วย `openssl rand -base64 32` จากนั้นรัน `npm run auth:owner` ใน Terminal ที่พิมพ์โต้ตอบได้ กรอกรหัสผ่าน 12–128 ตัวอักษรสองครั้ง โดยข้อความจะถูกซ่อนไว้ ตัวช่วยจะสร้างหรือตรวจบัญชี แล้วบันทึก `OWNER_NEON_USER_ID` ลง `.env.local` แบบ atomic ด้วยสิทธิ์ `0600` รหัสผ่านส่งให้ Neon Auth เท่านั้น ไม่เขียนลงไฟล์ค่าตั้ง อาร์กิวเมนต์คำสั่ง ที่เก็บข้อมูลเบราว์เซอร์ หรือ log
5. การติดตั้งใหม่ใช้ `owner@searchpilot.invalid` เป็น **ตัวระบุบัญชีภายในสำหรับ SDK** เพราะ API รหัสผ่านของ Neon ต้องการตัวระบุรูปแบบอีเมล ผู้ใช้กรอกเพียงชื่อผู้ใช้และรหัสผ่านในแอป ไม่ต้องใช้อีเมล Google ส่วนตัวเพื่อเข้าแอป
6. เมื่อสร้างเจ้าของแล้ว ให้ปิด sign-up ใน Neon แต่คง Email & Password sign-in ไว้ CLI ทางการรองรับ `neon neon-auth config email-password update --disable-sign-up` บน branch ที่เชื่อมไว้ ปิด social provider ที่ไม่ใช้ด้วย แอปบล็อกเส้นทางสมัครสมาชิก social login การเข้าโดยอีเมลโดยตรง และเส้นทางจัดการผู้ใช้ ผ่าน proxy ได้เฉพาะการอ่านเซสชันและออกจากระบบ
7. รัน `npm run db:migrate` กับ branch สำหรับพัฒนา แล้วเปิดเว็บและ worker ตารางธุรกิจอยู่ใน schema `public` เท่านั้น Prisma ไม่ได้เป็นผู้จัดการหรือทำ migration ให้ `neon_auth`

คำขอเข้าสู่ระบบต้องมาจาก origin เดียวกับแอป ตรวจรูปแบบข้อมูล และจำกัด 20 ครั้งต่อนาที เซิร์ฟเวอร์จับคู่ชื่อผู้ใช้ที่ตั้งไว้กับบัญชี Neon ไม่ใช้ค่าอีเมลที่ผู้ใช้ส่งมาเลือกบัญชี เซสชันต้องยังใช้ได้ และ user ID ต้องตรงกับ `OWNER_NEON_USER_ID` ที่ผูกไว้

ตัวระบุอีเมลภายในไม่ได้ให้สิทธิ์ด้วยตัวเอง การไม่ยืนยันอีเมลนี้จึงไม่ข้ามการตรวจเจ้าของ บัญชีที่ไม่ใช่เจ้าของได้รับ `403` ส่วนเซสชันที่ไม่มีหรือหมดอายุได้รับ `401`

### กรณีมีระบบใช้งานอยู่แล้ว

ใช้ Neon owner user ID และฐานข้อมูลเดิม ตั้ง `OWNER_AUTH_EMAIL` เป็นอีเมลเข้าสู่ระบบของบัญชีเดิม โดยยังรองรับ `OWNER_GOOGLE_EMAIL` เพื่อย้ายจากการตั้งค่าเก่า เปิด password sign-in แล้วตั้งหรือรีเซ็ตรหัสผ่านของ **บัญชีเดิมนั้น** ผ่านระบบจัดการ Neon

คง `OWNER_NEON_USER_ID` เดิมไว้ ตัวช่วยสร้างบัญชีจะไม่แทนที่เจ้าของที่ผูกไว้ด้วยบัญชีอื่น ไม่เขียนทับความเป็นเจ้าของข้อมูลธุรกิจหรือโทเคน Google ตัวระบุภายในแบบสงวนรับอีเมลกู้บัญชีไม่ได้ หากลืมรหัสผ่านต้องจัดการผ่าน Neon

Preview branch ต้องใช้ URL ฐานข้อมูล/Auth ค่าลับ และบัญชีเจ้าของของ branch นั้น ระบบ production ควรใช้ branch แยก ห้ามรัน `prisma migrate reset` หรือ `db push --accept-data-loss` กับฐานข้อมูลร่วมกันหรือ production ตรวจ SQL และสร้างจุดกู้คืนก่อน migration จริง และจำกัด migration ในอนาคตไว้เฉพาะ `public`

## 2. เชื่อมต่อ Search Console ด้วย Google OAuth

1. เปิด **Google Search Console API** ในโปรเจกต์ Google Cloud
2. ตั้งหน้าขอความยินยอม OAuth สำหรับแอปส่วนตัวแบบ External ให้เพิ่มบัญชี Google ของเจ้าของเป็น test user refresh token ในโหมด Testing อาจหมดอายุ หากต้องการซิงก์ต่อเนื่องโดยไม่มีผู้ใช้อยู่หน้าเว็บ ให้ใช้สถานะเผยแพร่หรือการตั้งค่า Internal ที่เหมาะสม และทำตามข้อกำหนดการตรวจแอปของ Google
3. สร้าง OAuth client ชนิด **Web application** สำหรับ GSC โดยใช้ redirect URI สำหรับพัฒนาให้ตรงทุกตัว:

   ```text
   https://localhost:3000/api/google/callback
   ```

4. ใส่ `GOOGLE_GSC_CLIENT_ID`, `GOOGLE_GSC_CLIENT_SECRET` และ `GOOGLE_GSC_REDIRECT_URI` ใน `.env.local` สำหรับ production ต้องใช้ `https://YOUR_HOST/api/google/callback` ให้ตรงกันทั้งใน Google Console และค่าตั้งเซิร์ฟเวอร์
5. สร้าง `GOOGLE_TOKEN_ENCRYPTION_KEY` ด้วย `openssl rand -base64 32` แล้วเก็บเป็นค่าลับของเซิร์ฟเวอร์อย่างถาวร หากเปลี่ยนคีย์ ต้องใช้คีย์เก่าถอดรหัสและเข้ารหัสโทเคนเดิมใหม่ หรือเชื่อมต่อ Google ใหม่ การเปลี่ยนคีย์โดยไม่ย้ายข้อมูลจะทำให้โทเคนเดิมอ่านไม่ได้
6. เข้าเมนู **ตั้งค่า → เชื่อมต่อ Search Console** อนุญาตสิทธิ์อ่านข้อมูล แล้วกด **ค้นหาเว็บไซต์** และเลือกเว็บไซต์เริ่มต้นได้
7. ไป **ประวัติการซิงก์** เพิ่มงานดึงข้อมูลย้อนหลัง โดยค่าเริ่มต้นคือ 90 วัน และเปิด worker เพื่อประมวลผล

สิทธิ์ที่ขอคือ `https://www.googleapis.com/auth/webmasters.readonly` การเข้าแอปและการอนุญาต GSC เป็นคนละขั้นตอน

OAuth ใช้ state ที่ผูกกับเจ้าของและคุกกี้ `HttpOnly`/`SameSite` บันทึก state แบบใช้ครั้งเดียว รองรับ PKCE S256 และ offline access พร้อมเข้ารหัส refresh token ด้วย AES-256-GCM ซึ่งผูกข้อมูลยืนยันกับเจ้าของ โทเคนนี้ไม่ถูกส่งเข้า JSON ฝั่งเบราว์เซอร์ ไม่อยู่ใน localStorage และไม่พิมพ์ใน log

Callback ตรวจ scope ที่ได้รับจริง หาก Google ไม่ส่ง refresh token ใหม่ จะเก็บโทเคนเดิมเฉพาะเมื่อยืนยันได้ว่าเป็น subject เดียวกัน หากไม่มี subject หรือบัญชีเปลี่ยน ต้องเชื่อมต่อใหม่พร้อมขอความยินยอมเพื่อไม่ให้ปะปนสิทธิ์ ค่า `googleAccountId` เป็น null ได้ เพราะ scope ขั้นต่ำของ GSC ไม่รับประกันข้อมูลระบุตัวตน

### ยกเลิกและเชื่อมต่อใหม่

การยกเลิกจะเพิกถอนสิทธิ์ Google ลบข้อมูลรับรอง และยกเลิกงานในคิวหรืองานที่กำลังทำ โดยเก็บข้อมูลวิเคราะห์ย้อนหลังไว้ หากสิทธิ์ถูกเพิกถอนไปแล้วและ Google ตอบ `invalid_token` ยังยกเลิกการเชื่อมต่อในแอปได้ แต่หากเครือข่ายล้มเหลว จะเก็บข้อมูลรับรองไว้และแจ้งว่าไม่สำเร็จ

การเพิกถอนของ Google อาจมีผลกับ OAuth clients ใน Cloud project เดียวกัน หากมีแอปอื่นใช้สิทธิ์ร่วมกัน ควรแยกโปรเจกต์สำหรับ GSC เมื่อพบ Google `401`/`invalid_grant` ระบบจะทำเครื่องหมายให้เชื่อมต่อใหม่ ส่วน `403` จากโควตา, `429` และ `5xx` ชั่วคราวระหว่างซิงก์จะลองใหม่โดยเพิ่มเวลารอ

## 3. งานซิงก์เบื้องหลังและการ deploy

นำ Next.js ขึ้น Vercel แล้วตั้ง Environment Variables ฝั่งเซิร์ฟเวอร์ กำหนด `NEXT_PUBLIC_APP_URL` เป็น origin สาธารณะที่ใช้จริง ค่านี้ไม่ใช่ความลับ แต่ห้ามเติม `NEXT_PUBLIC_` หน้าชื่อตัวแปรที่เป็นข้อมูลรับรอง

ใช้ migration ที่ตรวจแล้วในขั้นตอน release ก่อนให้บริการโค้ดใหม่ `npm run build` สร้าง Prisma Client แต่ **ไม่ได้ทำ migration ให้ production**

### เปิด worker แบบต่อเนื่อง

แนวทางหลักคือรัน Node service บนโฮสต์ที่เลือก โดยใช้คำสั่ง:

```sh
npm ci
npm run db:generate
npm run worker
```

Worker ต้องใช้ค่าฐานข้อมูล Google OAuth และคีย์เข้ารหัสชุดเดียวกับเว็บ โดยจะจัดคิวอัปเดตข้อมูลที่สรุปแล้วย้อนหลัง 7 วัน วันละครั้งตาม UTC ตรวจคิว และประมวลผลครั้งละหนึ่งหน้าข้อมูลจาก Google ไม่ต้องเข้าสู่ระบบค้างไว้ และเมื่อรีสตาร์ตจะทำต่อจากความคืบหน้าที่บันทึกไว้

**การกดซิงก์เป็นเพียงการเพิ่มงานในคิว** หากไม่เปิด worker หรือตัวตั้งเวลา งานจะค้างที่ `QUEUED` และยังไม่มีข้อมูลใหม่ แม้หน้าเว็บเปิดได้ตามปกติ

### ใช้ตัวตั้งเวลาแทน worker

เรียก `GET /api/cron` ทุกนาที พร้อม header `Authorization: Bearer YOUR_CRON_SECRET` โดย secret ต้องมีอย่างน้อย 32 ตัวอักษร แต่ละครั้งจะจัดคิวงานรายวันที่เข้าเกณฑ์ และทำงาน **หนึ่งขั้นตอนที่จำกัดขนาดไว้** ไม่ใช่ดึงข้อมูลย้อนหลังทั้งหมดในครั้งเดียว

`vercel.json` ตั้ง Cron ทุกนาทีไว้ ต้องใช้แพ็กเกจ Vercel ที่รองรับความถี่นี้ หากแพ็กเกจไม่รองรับ ให้เอาการตั้งค่า Cron นี้ออก แล้วรัน worker แยกหรือใช้ตัวตั้งเวลาภายนอกที่เรียกบ่อยพอ ตั้ง `CRON_SECRET` ใน Vercel เพื่อให้ส่ง header ยืนยันสิทธิ์ การเรียกเพียงวันละครั้งไม่เพียงพอที่จะประมวลผลข้อมูลย้อนหลังชุดแรกได้รวดเร็ว และห้ามใส่ secret ใน query string

### ความคืบหน้าและการกู้คืนงาน

PostgreSQL partial unique index จำกัดให้แต่ละเว็บไซต์มีงานที่กำลังดำเนินการได้หนึ่งงาน Worker รับงานด้วย `FOR UPDATE SKIP LOCKED` ใช้สิทธิ์ครอบครองงานที่หมดอายุได้ และตรวจ fencing token ภายใต้ transaction lock เพื่อป้องกัน worker เก่าเขียนผลทับ worker ใหม่

แต่ละขั้นตอนดึงข้อมูลหนึ่งวัน หนึ่งชุด และหนึ่งหน้าข้อมูล โดย API มี timeout 60 วินาที การพักข้อมูลชั่วคราว เผยแพร่ผลรายวัน และอัปเดต checkpoint ทำภายใน transaction จึงทำขั้นตอนเดิมซ้ำหลังรีสตาร์ตได้อย่างปลอดภัย Worker ที่หมดสิทธิ์แล้วไม่สามารถเผยแพร่ข้อมูลได้

แต่ละช่วงข้อมูลยอมให้ล้มเหลวได้ถึง 6 ครั้ง เริ่มรอ 30 วินาทีและเพิ่มแบบ exponential สูงสุดหนึ่งชั่วโมง งานที่ล้มเหลวสามารถลองใหม่จาก checkpoint ได้

### ชุดข้อมูลและช่วงวันที่

| ชุดข้อมูล | มิติที่ดึง |
| --- | --- |
| `SITE_DAILY` | วันที่ |
| `QUERY_DAILY` | วันที่และคำค้นหา |
| `PAGE_DAILY` | วันที่และหน้าเว็บ |
| `QUERY_PAGE_DAILY` | วันที่ คำค้นหา และหน้าเว็บ |

ทุกคำขอใช้ `type=web`, `dataState=final` และวิธีรวมผลตามเว็บไซต์หรือหน้าเว็บที่เหมาะสม ดึงครั้งละ 25,000 แถว หากถึงเพดาน 50,000 แถวต่อวันต่อชุดข้อมูล จะบันทึกว่าข้อมูลถูกตัดทอน แม้ยังไม่ถึงเพดาน Google ก็ส่งคืนเฉพาะแถวยอดนิยมและอาจละเว้นคำค้นหาที่ไม่ระบุตัวตนหรือแถวอื่น จึงไม่รับประกันว่าครอบคลุมทุกคำค้นหา เก็บ URL และรหัสเว็บไซต์ตามที่ Google ส่งกลับโดยไม่เปลี่ยนรูปแบบ

ช่วงวันที่เริ่มต้นสิ้นสุดที่ 3 วันก่อนตามเวลาแปซิฟิก โดยขอเฉพาะข้อมูลที่สรุปแล้ว ตัวกรอง **วันนี้** เลือกวันปัจจุบันตามเวลาแปซิฟิก และแจ้งว่าระบบซิงก์แบบนี้ยังไม่มีข้อมูลวันนี้ พร้อมปิดปุ่มซิงก์ Dashboard สำหรับวันนั้น จึงไม่ใช่ข้อมูลเรียลไทม์

หากยังไม่มีงานที่สำเร็จครอบคลุมช่วงวันที่เลือก จะแสดงคำเตือนเรื่องความครบถ้วนของข้อมูล ไม่สร้างแถวแทนวันที่ Google ไม่ส่งกลับ และไม่ถือว่าเป็นศูนย์โดยอัตโนมัติ `lastSyncAt` อัปเดตเมื่อทั้ง 4 ชุดเสร็จแล้ว

CTR = คลิกทั้งหมด ÷ การแสดงผลทั้งหมด อันดับเฉลี่ยถ่วงน้ำหนักด้วยการแสดงผลของข้อมูลที่รวมกันได้ ยอดรวมเว็บไซต์ใช้ `SITE_DAILY` เสมอ ไม่บวกยอดแถวคำค้นหาแทน

## รายงานและเกณฑ์วิเคราะห์ SEO

หน้า **คีย์เวิร์ด** และ **หน้าเว็บ** รองรับการค้นหา ตัวกรองตัวเลข การเรียง และแบ่งหน้าฝั่งเซิร์ฟเวอร์หน้าละ 25 รายการ แสดงการเปลี่ยนแปลงจากช่วงก่อนหน้าที่มีจำนวนวันเท่ากัน ประวัติรายวัน URL/คำค้นหาที่เกี่ยวข้อง และส่งออก CSV ได้สูงสุด 10,000 แถวที่ผ่านตัวกรอง

CSV escape ค่าในเซลล์และป้องกันค่าที่อาจทำงานเป็นสูตรในสเปรดชีต กราฟเปรียบเทียบหน้าเว็บใช้ข้อมูล `PAGE_DAILY` ที่รวมแยกกัน ประเภทเป้าหมายหน้าเว็บได้แก่ Product, Category, Blog, Landing Page และ Other โดยแสดงชื่อเป็นไทยในหน้าจอ และกำหนดความสัมพันธ์ระหว่างคีย์เวิร์ดกับ URL หลักได้

หน้า **โอกาสปรับปรุง** กรองและเรียงผลฝั่งเซิร์ฟเวอร์ แบ่งหน้าละ 10 รายการ พร้อมยอดรวม ปุ่มก่อนหน้า/ถัดไป เปลี่ยนตัวกรองหรือการเรียงจะกลับหน้าแรก หากผลลัพธ์ลดลง ระบบจะปรับไปหน้าสุดท้ายที่ยังมีข้อมูล

### เกณฑ์วิเคราะห์ 7 แบบ

ใช้ข้อมูลที่มีการแสดงผลมากที่สุด **ไม่เกิน 5,000 คำค้นหา หน้าเว็บ และความสัมพันธ์คำค้นหา–URL ต่อชุดข้อมูลต่อช่วง 28 วัน** รวมช่วงก่อนหน้าและช่วงที่เก่ากว่าซึ่งมีจำนวนวันเท่ากัน เพื่อดูแนวโน้ม ขอบเขตนี้แสดงในหน้าจอ เรียกวิเคราะห์จากหน้าโอกาสปรับปรุงหลังซิงก์แล้ว ไม่มีการเรียก AI API

เกณฑ์และคะแนนอยู่ใน `src/lib/seo/analyzer.ts` รับข้อมูลเข้าและคืนผลวิเคราะห์โดยไม่ผูกกับการเข้าถึงฐานข้อมูล

- **โอกาสปรับปรุงเร็ว:** อันดับ 4–15
- **ใกล้หน้าแรก:** อันดับ 11–20
- **CTR ต่ำ:** ต่ำกว่า 60% ของค่ามัธยฐานจากรายการอื่นอย่างน้อย 5 รายการ ในช่วงอันดับเดียวกันที่แบ่งทุก 3 อันดับภายในเว็บไซต์นี้ ส่วนผสมของแบรนด์ อุปกรณ์ และเจตนาการค้นหาอาจต่างกัน จึงเป็นสัญญาณให้ตรวจ ไม่ใช่เส้น CTR มาตรฐานสำหรับทุกกรณี
- **ยอดคลิกลดลง:** คลิกลดอย่างน้อย 20% โดยช่วงฐานต้องมีคลิกถึงขั้นต่ำ
- **การแสดงผลเพิ่มขึ้น:** การแสดงผลเพิ่มอย่างน้อย 30% แต่คลิกเพิ่มไม่เกิน 10%
- **หน้าเว็บอาจแข่งขันกันเอง:** มีหลาย URL ที่แต่ละ URL ผ่านขนาดตัวอย่างขั้นต่ำ และมีอย่างน้อย 15% ของการแสดงผลคำค้นหาที่สังเกตได้ พร้อมข้อมูล URL หลัก การทับซ้อนไม่ได้แปลว่าส่งผลเสียเสมอไป
- **เนื้อหาเสื่อมประสิทธิภาพ:** คลิกลดอย่างน้อย 15% ในการเปรียบเทียบสองช่วงต่อเนื่องที่ยาวเท่ากัน โดยช่วงฐานต้องผ่านเกณฑ์ขั้นต่ำ

ค่าเริ่มต้นคือการแสดงผล 200 ครั้ง และคลิกช่วงฐาน 20 ครั้ง ผลวิเคราะห์มีขนาดตัวอย่าง ความเชื่อมั่น ข้อมูลประกอบ และข้อเสนอให้ตรวจทาน ปรับเกณฑ์แยกตามเว็บไซต์ได้ในเมนูตั้งค่า

### การให้คะแนน

คะแนน 0–100 เป็นเกณฑ์ประมาณเพื่อจัดลำดับการตรวจทาน โดยคำนวณอย่างเปิดเผย:

```text
volume = min(1, log10(1 + impressions) / 5)
position = max(0, 1 - abs(averagePosition - 8) / 25)
impact = clamp(ruleTrendSignal, 0, 1)
confidence = min(.95, .5 + .45 * min(1, max(currentImpressions, previousImpressions) / 2000))
score = round(100 * min(1, .35*volume + .20*position + .30*impact + .15*confidence) * confidence)
```

CTR ต่ำใช้ `1 - observedCTR / peerMedianCTR` เป็นผลกระทบ และลดความเชื่อมั่นด้วยตัวคูณ `.85` การลดลงใช้สัดส่วนที่สังเกตได้ ส่วนโอกาสปรับปรุงเร็ว ใกล้หน้าแรก การแสดงผลเพิ่ม เนื้อหาเสื่อม และการทับซ้อน ใช้สัญญาณ `.5`, `.4`, `.6`, `.7` และ `.5` ตามลำดับ ความเชื่อมั่นของการทับซ้อนคือ `.6`

หากไม่มีแถวข้อมูลในช่วงปัจจุบัน จะลดความเชื่อมั่นด้วยตัวคูณ `.6` และระบุให้ตรวจยืนยันใน GSC คะแนนไม่ใช่การคาดการณ์อันดับ Google

Fingerprint ที่คงที่จากเกณฑ์ คำค้นหา URL และบริบทช่วยป้องกันผลซ้ำ รายการที่ละเว้นยังคงถูกละเว้นเมื่อวิเคราะห์ใหม่ รายการที่ไม่พบแล้วจะถูกทำเครื่องหมายว่าแก้ไขแล้ว และรายการที่กลับมาพบอีกจะเปิดใหม่

### งาน SEO การบันทึกการเปลี่ยนแปลง และการตรวจ URL

งาน SEO รองรับแก้ไข ลบ สถานะ ความสำคัญ และลิงก์กลับไปยังโอกาสปรับปรุง วันที่เสร็จจะอัปเดตเมื่อเข้าสู่หรือออกจากสถานะ `DONE`

รายละเอียดหน้าเว็บบันทึกการปรับปรุง SEO ได้ และเปรียบเทียบ 28 วันก่อนหน้ากับ 28 วันนับจากวันที่เปลี่ยนแปลง ช่วงหลังอาจยังไม่ครบ หน้าจอจะแจ้งว่าความสัมพันธ์ของข้อมูลไม่ได้ยืนยันว่าการเปลี่ยนแปลงเป็นสาเหตุของผลลัพธ์

การตรวจสอบ URL เก็บฟิลด์เกี่ยวกับการจัดทำดัชนีทั้งหมดที่ Google ส่งกลับ **ไม่ใช่** การทดสอบ URL ปัจจุบัน เครื่องมือ crawler หรือเครื่องมือขอจัดทำดัชนี ส่วน Sitemaps เป็นความสามารถเสริมที่ยังไม่ได้ทำ

Playwright ใช้คุกกี้เซสชันที่ลงนามเข้ากันได้กับ SDK ด้วย secret เฉพาะการทดสอบ และจำลองคำตอบ API ในเบราว์เซอร์ ไม่เพิ่มทางข้ามการยืนยันตัวตนในแอป และไม่ต้องใช้ข้อมูลรับรอง Google ของ production

## รายการตรวจระบบจริง

ต้องใช้บัญชีและบริการจริงเพื่อยืนยันรายการต่อไปนี้:

- ใช้ migration บน Neon branch ใหม่ และตรวจว่า `neon_auth` ยังอยู่ครบ
- เข้าสู่ระบบด้วยชื่อผู้ใช้/รหัสผ่านจริง โหลดเซสชันซ้ำ ทดสอบหมดอายุ ออกจากระบบ และปฏิเสธบัญชีอื่น
- ทดสอบ callback ขอสิทธิ์ GSC ค้นหาเว็บไซต์ ต่ออายุโทเคน เพิกถอนสิทธิ์ และเชื่อมต่อใหม่
- ดึงข้อมูลย้อนหลังให้เสร็จ เทียบสถิติกับ GSC โดยใช้วันที่รายงานและวิธีรวมผลตรงกัน แล้วตรวจการอัปเดตตามเวลาหลังออกจากระบบ
- ตรวจ URL จริง สร้าง/แก้ไข/ทำงานให้เสร็จ และทดสอบตัวกรองกับการเปรียบเทียบคีย์เวิร์ด/หน้าเว็บ
- ตรวจ pagination ของโอกาสปรับปรุง โดยเฉพาะหน้าสุดท้าย การเปลี่ยนตัวกรอง และผลลัพธ์ที่ลดลงหลังละเว้นรายการ
- Deploy ด้วยค่าลับ production ตรวจว่า worker หรือตัวตั้งเวลาทำงาน และคำขอ Cron ที่ไม่มีสิทธิ์ได้รับ `401`

เทสต์จำลองหรือ build ที่สำเร็จไม่สามารถยืนยันรายการภายนอกเหล่านี้ได้ อย่าถือว่าระบบผ่านการตรวจ production จนกว่าจะตรวจครบ

- [Neon Auth สำหรับ Next.js](https://neon.com/docs/auth/quick-start/nextjs-api-only) และ [การเชื่อม SDK ตามข้อกำหนดเดิม](https://github.com/neondatabase/neon-js/blob/main/packages/auth/NEXT-JS.md)
- [การตั้งค่าอีเมล/รหัสผ่านของ Neon Auth](https://neon.com/docs/cli/neon-auth)
- [Prisma 7 บน Neon](https://neon.com/docs/guides/prisma) — CLI, Client และ adapter ในโปรเจกต์ใช้รุ่น 7.10.1 ตรงกัน หากอัปเกรดให้ตรวจความเข้ากันได้ก่อน
- [ข้อกำหนด Search Analytics query](https://developers.google.com/webmaster-tools/v1/searchanalytics/query), [การดึงข้อมูลและความครอบคลุม](https://developers.google.com/webmaster-tools/v1/how-tos/all-your-data), [การตรวจสอบ URL](https://developers.google.com/webmaster-tools/v1/urlInspection.index/inspect)
- [Google OAuth สำหรับเว็บเซิร์ฟเวอร์](https://developers.google.com/identity/protocols/oauth2/web-server)

Production build ใช้ Webpack ที่ Next.js รองรับ ซึ่งทำงานได้ในสภาพแวดล้อมที่จำกัดพอร์ตของ subprocess จาก Turbopack รุ่น dependency ถูกตรึงใน `package-lock.json` เพื่อให้ติดตั้งซ้ำได้ `.npmrc` รองรับ dependency graph ของ UI เสริมใน SDK โดยไม่สร้าง Better Auth server แยก ตรวจการแก้ lockfile และรันการตรวจทั้งหมดใหม่หลังอัปเกรด SDK

## บันทึกผลการตรวจล่าสุด

หลังเพิ่ม pagination ของโอกาสปรับปรุง: **Vitest ผ่าน 90 เทสต์ใน 19 ไฟล์** พร้อม typecheck, lint และ production build โดยครอบคลุมการจับคู่ชื่อผู้ใช้ การตรวจเจ้าของจาก user ID การบล็อก Auth endpoint สาธารณะ และการสร้างบัญชีเจ้าของอย่างปลอดภัยด้วย ดูประวัติงานยืนยันตัวตนได้ที่ [แผนชื่อผู้ใช้และรหัสผ่าน](docs/superpowers/plans/2026-11-16-username-login.md)

Migration และ SQL วิเคราะห์จริงผ่านการทดสอบกับ PostgreSQL ชั่วคราว รวม URL ยาวและคำค้นหา Unicode ก่อนหน้านี้ตรวจ browser bundles แล้วไม่พบการอ้างอิงค่าตั้งลับฝั่งเซิร์ฟเวอร์

ระหว่างพัฒนามีการยืนยัน migration บน Neon การสร้างบัญชีเจ้าของ และการซิงก์ข้อมูล GSC จริงแล้ว แต่ไม่ใช่การรับรองรายการตรวจ production ทั้งหมด

มี Playwright **10 สถานการณ์** และ CI workflow ให้ใช้งาน แต่การทดสอบเบราว์เซอร์ใน sandbox ถูกจำกัดการเปิดเซิร์ฟเวอร์/เข้าถึงเบราว์เซอร์ จึงยังไม่ยืนยันว่า E2E หรือการตรวจภาพหน้าจอผ่าน ระบบยังไม่ได้ deploy ขึ้น Vercel ไฟล์ `.env.local` และ `certificates/` ถูกละเว้นจากการควบคุมเวอร์ชัน และต้องไม่เผยแพร่ค่าลับของระบบจริง
